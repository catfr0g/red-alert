# Инструкции для AI-агентов

## Контекст проекта

Red Alert — прототип инструмента для авторизованного защитного тестирования (red teaming) агентных ИИ-систем. Система должна помогать воспроизводимо проверять, как недоверенный ввод влияет на контекст, память, выбор и вызов инструментов, состояние агента и последующие действия.

Перед изменением поведения проекта прочитай:

- [`openspec/config.yaml`](openspec/config.yaml) — рабочие правила OpenSpec;
- [`docs/business/context.md`](docs/business/context.md) — контекст кейса;
- [`docs/business/glossary.md`](docs/business/glossary.md) — определения терминов;
- [`docs/business/case-description.md`](docs/business/case-description.md) — описание задачи;
- релевантные материалы в [`docs/business/`](docs/business/).

Основные артефакты OpenSpec — `proposal.md`, `design.md`, спецификации и `tasks.md` — пиши на русском языке. Названия change, файлов, команд, кода и устоявшихся технических терминов могут оставаться на английском.

Все диаграммы в артефактах OpenSpec (`proposal.md`, `design.md`, спецификации и `tasks.md`) оформляй в fenced-блоках Markdown с языком `mermaid`; текстовые/ASCII-схемы и другие языки описания диаграмм не используй.

## OpenSpec-процесс

- Для новой функциональности, изменения поведения или архитектуры сначала создай либо продолжи change в `openspec/changes/<change-name>/`.
- Используй схему `spec-driven`: proposal → design/specs → tasks → implementation → validation; содержимое артефактов оформляй на русском.
- Перед реализацией прочитай все доступные артефакты активного change и следуй их требованиям.
- Не реализуй требования, которых нет в артефактах, молча: зафиксируй их в change или запроси уточнение.
- После выполнения задачи сразу отметь её как выполненную в `tasks.md`.
- Перед завершением запускай OpenSpec-валидацию и проверяй соответствие реализации сценариям.
- Не редактируй основной spec напрямую для локального изменения: сначала опиши delta в change, а синхронизацию выполняй через OpenSpec.
- Архивируй change только после завершения реализации и явного решения пользователя.

## Инженерные правила

- Используй Python 3.14+ и учитывай настройки из `pyproject.toml`.
- Пиши документацию, описания решений и комментарии на упрощённом техническом языке: коротко, точно, без лишнего жаргона и теории.
- Следуй YAGNI: не реализуй возможности «на будущее», если они не нужны текущей спецификации.
- Следуй KISS: выбирай самое простое решение, которое удовлетворяет требованиям и остаётся понятным.
- Следуй DRY: не дублируй знания и логику, но не создавай преждевременные абстракции ради устранения одного повтора.
- Сохраняй минимальный объём изменений; не делай несвязанных рефакторингов и переименований.
- Не добавляй зависимости, абстракции и конфигурационные параметры без требования change.
- Новые публичные интерфейсы должны иметь ясные типы, проверяемое поведение и документацию там, где это необходимо.
- На каждую новую фичу добавляй автоматические тесты. Фича не считается завершённой, пока её тесты не написаны и не проходят.
- Для каждого существенного поведения добавляй проверку или явно фиксируй причину, почему она пока невозможна.
- Сохраняй воспроизводимость: предпочитай детерминированные фикстуры, mock-инструменты, синтетические данные и изолированный тестовый контур.

## Безопасность

- Работай только в авторизованной, изолированной тестовой среде.
- Не используй реальные банковские операции, учётные данные, персональные данные или боевые ресурсы.
- Финансовые и другие внешние действия в прототипе должны выполняться через безопасные mock-реализации, если спецификация явно не требует иного.
- Не помещай секреты в репозиторий, логи, фикстуры или артефакты OpenSpec.
- Отчёт должен сохранять причинно-следственную цепочку: вход → контекст/память → решение → вызов инструмента → изменение состояния → доказательство результата.

## Проверка результата

Минимальная проверка после изменений:

1. проверить формат и статус OpenSpec через CLI;
2. запустить доступные тесты;
3. для изменённых Python-файлов выполнить проверку компиляции;
4. убедиться, что изменения покрывают требования и сценарии активного change.

Если проверка невозможна, укажи это явно вместе с причиной и оставшимся риском.
