# Agentic Red Teaming
## 1. Целевая аудитория (Кто пользователь?)
### Основной пользователь
#### Департамент кибербезопасности банка
Роли: Security Engineers, Red Team Specialists, Application Security Architects

Задача: Валидация и тестирование систем генеративного ИИ перед внедрением в production

Формат взаимодействия: CLI-отчёты, JSON-логи, интеграция с CI/CD для регрессионного тестирования

### Расширенная аудитория
#### Бизнес-заказчики и продакт-менеджеры
Роли: Product Owners, AI Solution Architects, Compliance Officers

Задача: Развёртывание агентов с доступом к чувствительным данным или критическим действиям (финансовые операции, медицинские консультации, юридические советы)

Формат взаимодействия: Отчёты с визуализацией атак, дашборды с метриками ASR, презентационные материалы

## 2. Проблематика (Что болит?)
| № | Проблема | Описание | Последствия для бизнеса |
|---|----------|----------|--------------------------|
| 1 | Слепые зоны безопасности, иллюзия защищенности | Существующие инструменты (Garak, Promptfoo, Llamator) проверяют только цепочку Запрос → Ответ. Они не видят, как атака "запоминается" агентом и влияет на его будущие действия | Атака может остаться незамеченной, пока не произойдёт реальный инцидент с финансовыми потерями, а руководство уже приняло решение о внедрении/внедрило |
| 2 | Отсутствие инструментов для проверки долговременной памяти - сложность ручной проверки | Цепочка действий агента (Память → Планирование → Инструменты → Изменение состояния) слишком ресурсозатратна для ручной проверки всех сценариев. Невозможно перебрать все комбинации каналов доставки (запрос, документ, веб-страница, результат инструмента) | Специалисты тратят силы на воспроизведение одного сценария, пропуская десятки других уязвимостей |
| 3 | Сжатые сроки | В ситуации с ручной проверкой специалисты могут тратить в лучшем случае дни, в худшем недели на проверку защитных механизмов, у бизнеса времени на это может не быть | В условиях сжатых сроков либо выпуск непроверенного незащищенного агента, либо неспособность выпустить агента быстрее конкурентов |
| 4 | Отсутствие сквозной метрики | Нет единого способа измерить устойчивость агента к компрометации. Attack Success Rate (ASR) для чат-ботов не учитывает отложенные атаки через память | Невозможно объективно сравнить версии агентов или эффективность защитных механизмов |

## 3. Ценностное предложение (Почему мы?)
### Ключевое отличие: Видение "Сквозной атаки". 

**Что мы обнаруживаем:**
1. Отравление долговременной памяти — вредоносная инструкция сохраняется между сессиями или даже между пользователями
2. Влияние на планирование — атака изменяет выбор инструмента или его аргументы
3. Кросс-сессионные эффекты — компрометация распространяется на других пользователей через общую память

### Автоматизация полного цикла
Вместо ручного написания сценариев мы предоставляем просто "кнопку" для:

| Этап | Что делаем | Результат |
|------|------------|-----------|
| 1. Анализ | Автоматическое моделирование угроз на основе схемы агента | Карта поверхностей атаки |
| 2. Генерация | LLM создаёт адаптивные многошаговые сценарии | Набор тестовых кейсов |
| 3. Исполнение | Автоматический прогон атак через выбранные каналы | Трассировка всех действий |
| 4. Верификация | Проверка достижения цели (память, инструменты, состояние) | Объективная оценка |
| 5. Отчёт | Детальный анализ скомпрометированного состояния | Готовый документ с ASR |

### Измеримый результат: Attack Success Rate (ASR)
**Что измеряем:** Не просто "выдал ли агент вредоносный ответ?", а "изменилось ли состояние агента так, что это приведёт к выгоде атакующего?"

## 4. Гипотезы для проверки (Что мы предполагаем?)
### Продуктовые гипотезы

| ID | Гипотеза | Как проверим | Критерий успеха |
|----|----------|--------------|-----------------|
| H1 | Специалисту важнее увидеть изменённое состояние агента (память), а не просто вредоносный ответ | Предоставим два отчёта: один с финальным ответом, второй — с трассировкой состояния. Спросим, какой позволяет воспроизвести атаку | Специалист может точно указать момент и место компрометации по второму отчёту |
| H4 | Необходимо сравнение состояния до/после атаки и replay следующей сессии как доказательство отравления памяти | Сделаем снапшот памяти, доставим вредоносную инструкцию, завершим сессию, запустим триггерную сессию | Отчёт покажет запись, триггер и последствие с привязкой к конкретным шагам трассы |
| H6 | Единый формат сценария, доказательств и ASR позволяет сравнивать версии агента | Прогоним один набор атак на двух версиях тестового агента | Результаты воспроизводимы, различия видны, отчёт работает как regression test |
| H8 | Данные, собранные в процессе Agentic Red Teaming (трассировка атак, сценарии компрометации памяти, успешные цепочки действий), можно напрямую транслировать в формат защитных мер: политик безопасности, детекторов и правил для runtime-защиты. | На основе успешных атак из Red Teaming-сессии сгенерировать YAML-политики для OWASP Agent Memory Guard и правила детекции для SIEM, затем проверить их на том же стенде. | Скомпрометирующие агента атаки, обнаруженные Red Team-ом, приводят к появлению измеримых защитных контролов (детекторов, политик, alert-правил), которые можно воспроизвести и подтвердить на том же стенде. Система становится самосовершенствующейся через петлю обратной связи Red ↔ Blue |

### Технические гипотезы

| ID | Гипотеза | Как проверим | Критерий успеха |
|----|----------|--------------|-----------------|
| H2 — AI | По схеме приложения, инструментов, памяти и модели угроз AI сможет генерировать правдоподобные многошаговые цепочки атак через разные каналы доставки. | Запустить генератор на синтетическом агенте с заранее известными уязвимыми путями и провести экспертную оценку сценариев. | Генерируются сценарии, которые действительно достигают заданной цели, а не только вызывают подозрительный ответ. |
| H3 | Адаптивный планировщик (меняющий тактику на основе логов) повысит ASR | Сравним adaptive и fixed execution на одном наборе сценариев | ASR и/или покрытие уникальных путей выше у адаптивного режима |
| H5 | Цель атаки можно проверять формально по предикатам состояния, дополняя их AI-оценкой | Зададим цели вроде "изменён аргумент инструмента". Сравним rule-based и LLM-оценку | Успех определяется по фактическому состоянию/действию, а не теряется из-за нормального финального текста |
| H7 | Целевой агент можно безопасно и достаточно полно наблюдать: читать/сбрасывать память, перехватывать tool calls, видеть изменения состояния и запускать изолированные сессии. Без этого ASR и доказательство скрытой атаки будут ненадёжны. |	На первом техническом спринте подключить минимальный стенд и проверить полный цикл «seed → attack → new session → observe → reset». | Есть надёжный контрольный стенд, на котором можно воспроизводимо подтвердить или опровергнуть компрометацию без реальных финансовых операций и клиентских данных. |
| H9 | Использование LLM для генерации сценариев найдёт больше уязвимых путей, чем статический список промптов | Запустим генератор на агенте с известными уязвимостями. Сравним с ручным набором промптов | Генерируются сценарии, которые достигают цели, а не только вызывают подозрительный ответ |

H7 - **наиболее рискованная гипотеза**. У нас может не быть возможности запустить тестового агента отдельно от production, откатить агента в исходное состояние после атаки, наше тестирование может затронуть реальных пользователей.

## 5. Ключевые риски (Что может пойти не так?)
| Риск | Описание | План смягчения |
|------|----------|----------------|
| Наблюдаемость агента | Целевой агент может не предоставлять API для чтения памяти, перехвата tool calls и трассировки | В POC используем mock-агента с открытым интерфейсом. Для MVP уточним у заказчика доступы |
| Определение успеха | Без чётких правил подсчёта ASR оценка будет субъективной | Зафиксируем определение "целевого состояния" для каждого сценария на Q&A с заказчиком |
| Безопасность тестирования | Нельзя использовать реальные финансовые операции и клиентские данные | Все финансовые действия заменяем на безопасные моки. Используем синтетические данные |
| Стоимость прогонов | LLM-генерация и оценка могут быть дорогими при большом числе попыток | Используем self-hosted маленькие модели. Оптимизируем бюджет через количество итераций |

## 6. Метрики успеха продукта
| Метрика | Целевое значение | Способ измерения |
|---------|-----------------:|------------------|
| ASR (Attack Success Rate) | Более 60% на тестовом стенде | Доля успешных атак от общего числа попыток |
| Время подготовки сценария | Менее 10 минут | От запуска анализа до первого сгенерированного сценария |
| Воспроизводимость | 100% | Одинаковые результаты при повторном прогоне на том же агенте |
| Удовлетворённость пользователя | Более 8 из 10 | Опрос пилотных пользователей из департамента кибербезопасности |
