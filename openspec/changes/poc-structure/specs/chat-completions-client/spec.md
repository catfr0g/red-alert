# Возможность: клиент chat completions

## ADDED Requirements

### Requirement: клиент использует только chat completions ручку

Клиент ДОЛЖЕН (MUST) отправлять только POST-запросы на
http://localhost:8600/v1/chat/completions. Он НЕ ДОЛЖЕН обращаться к
GET /memory, POST /v1/sessions/{session_id}/finalize или любым другим
ручкам стенда.

Каждый запрос ДОЛЖЕН содержать заголовки Content-Type: application/json и
Authorization: Bearer <api-key>.

#### Scenario: Обычный chat-запрос

- **КОГДА** сценарий вызывает клиент с текстом пользователя и session_id
- **ТОГДА** клиент отправляет POST на точный URL с полями model, messages,
  session_id, auth_mode и stream=false

#### Scenario: Финализация через chat-запрос

- **КОГДА** сценарий просит финализировать сессию
- **ТОГДА** клиент отправляет на тот же URL отдельный запрос с messages,
  содержащим одну реплику с role=user и content=finalize

### Requirement: клиент формирует точное тело запроса

Клиент ДОЛЖЕН (MUST) поддерживать следующие поля тела:

- model — строка; для PoC используется genai-invest-assistant;
- messages — обязательный список объектов ChatMessage с обязательными строковыми
  полями role и content;
- session_id — непустая строка;
- auth_mode — vulnerable или protected; PoC использует vulnerable;
- stream — false.

Клиент НЕ ДОЛЖЕН использовать stream=true и не обязан реализовывать SSE в
рамках текущего change.

#### Scenario: Запрос payload

- **КОГДА** клиент отправляет payload для сессии A
- **ТОГДА** тело содержит session_id сессии A, auth_mode=vulnerable,
  stream=false и messages только с payload-репликой пользователя

#### Scenario: Запрос trigger

- **КОГДА** клиент отправляет trigger для сессии B
- **ТОГДА** тело содержит другой session_id сессии B и новый messages только
  с trigger-репликой пользователя

### Requirement: клиент разбирает нестриминговый ответ

При HTTP-статусе 2xx клиент ДОЛЖЕН (MUST) разобрать JSON и вернуть текст из
choices[0].message.content. Поле content ДОЛЖНО быть строкой. Идентификатор,
model и прочие поля ответа могут сохраняться в трассировке как метаданные, но
не заменяют проверку текстового content.

#### Scenario: Валидный ответ стенда

- **КОГДА** стенд возвращает успешный OpenAI-compatible ответ с
  choices[0].message.content
- **ТОГДА** клиент возвращает текст ответа и данные, необходимые для шага
  трассировки

#### Scenario: Невалидная структура ответа

- **КОГДА** успешный HTTP-ответ не содержит choices[0].message.content или
  content имеет нестроковый тип
- **ТОГДА** клиент возвращает protocol error, а сценарий не считает шаг
  успешным

### Requirement: ошибки HTTP и тайм-ауты видны вызывающему коду

Клиент ДОЛЖЕН (MUST) использовать конечный timeout, проверять HTTP-статус и
преобразовывать сетевые ошибки, тайм-ауты и статусы 4xx/5xx в типизированную
ошибку шага. Текст ошибки может включать код и безопасное тело ответа, но не
может включать API-ключ.

#### Scenario: Ошибка авторизации

- **КОГДА** стенд возвращает 401 или 403
- **ТОГДА** клиент возвращает ошибку HTTP-шагу и не создаёт текстовое
  доказательство успешного ответа

#### Scenario: Недоступный стенд

- **КОГДА** соединение завершается тайм-аутом или сетевой ошибкой
- **ТОГДА** клиент возвращает ошибку шага без повторной отправки запроса
