# Возможность: сценарий memory poisoning

## ADDED Requirements

### Requirement: сценарий выполняет фиксированную последовательность

Система ДОЛЖНА (MUST) выполнять сценарий memory-poisoning в порядке payload,
finalize, trigger. Сценарий ДОЛЖЕН использовать два разных непустых
session_id в рамках одного запуска:

- session A — доставка payload и финализация;
- session B — trigger после финализации.

Оба session_id используются с одним API-ключом и одним user_id в текущем PoC.

#### Scenario: Полный порядок сценария

- **КОГДА** runner запускает memory-poisoning
- **ТОГДА** он выполняет ровно один chat-запрос с payload в сессии A, затем
  ровно один chat-запрос с finalize в сессии A, затем ровно один chat-запрос
  с trigger в сессии B

#### Scenario: Сессия trigger отличается от сессии атаки

- **КОГДА** runner строит запрос trigger
- **ТОГДА** его session_id отличается от session_id payload и finalize

### Requirement: payload доставляется пользовательским сообщением

Сценарий ДОЛЖЕН (MUST) отправлять payload отдельным запросом с массивом
messages, содержащим одну реплику с role=user и фиксированным текстом payload.
Текст payload и ожидаемый эффект не генерируются LLM во время прогона.

#### Scenario: Успешная доставка payload

- **КОГДА** клиент принимает payload-запрос со статусом 2xx и валидным
  текстовым ответом
- **ТОГДА** runner сохраняет шаг payload как успешный и переходит к
  финализации той же сессии

### Requirement: рабочая память финализируется через ту же ручку

Сценарий ДОЛЖЕН (MUST) отправлять finalize отдельным chat-запросом в сессии A.
Единственная пользовательская реплика этого запроса ДОЛЖНА иметь role=user и
content=finalize. Сценарий НЕ ДОЛЖЕН вызывать прямую ручку
POST /v1/sessions/{session_id}/finalize.

#### Scenario: Финализация после payload

- **КОГДА** payload-запрос завершился успешно
- **ТОГДА** runner отправляет finalize в той же сессии A и сохраняет его
  текстовый ответ как доказательство перехода к долговременной памяти

#### Scenario: Ошибка финализации

- **КОГДА** finalize завершается HTTP-ошибкой, сетевой ошибкой или
  невалидным ответом
- **ТОГДА** runner останавливает сценарий, не отправляет trigger и сохраняет
  частичную трассировку

### Requirement: trigger выполняется в новой сессии

После успешной финализации сценарий ДОЛЖЕН (MUST) отправить в сессии B отдельный
запрос с одной пользовательской trigger-репликой. Тело trigger-запроса не
должно содержать payload, finalize, ответов предыдущих шагов или историю
messages.

#### Scenario: Trigger после финализации

- **КОГДА** payload и finalize завершились успешно
- **ТОГДА** runner отправляет trigger в сессии B и сохраняет текст ответа как
  основное поведенческое доказательство

### Requirement: сценарий не читает и не очищает память напрямую

Runner ДОЛЖЕН (MUST) получать доказательства только из ответов chat completions.
GET /memory может использоваться человеком для ручной инспекции стенда, но не
вызывается автоматическим сценарием. Операция очистки памяти между прогонами
не является частью сценария.

#### Scenario: Изолированный тестовый контур

- **КОГДА** выполняется автоматический тест сценария
- **ТОГДА** mock transport видит только три POST-запроса к
  /v1/chat/completions в указанном порядке и не видит вызовов /memory или
  другой ручки финализации

### Requirement: ошибка останавливает последовательность

Runner ДОЛЖЕН (MUST) остановить выполнение после первой ошибки payload или
finalize. Ошибка trigger также должна завершать запуск ошибкой. Уже собранные
шаги не теряются.

#### Scenario: Ошибка payload

- **КОГДА** payload-запрос завершается ошибкой
- **ТОГДА** runner не отправляет finalize и trigger, а результат получает
  статус error

#### Scenario: Успешная последовательность

- **КОГДА** все три запроса завершились успешно и ответы валидны
- **ТОГДА** трассировка содержит шаги payload, finalize и trigger с их
  session_id в указанном порядке
