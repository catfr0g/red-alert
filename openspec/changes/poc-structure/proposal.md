# Предложение: минимальный PoC отравления памяти

## Why

Репозиторий пока содержит только минимальную точку входа, а границы PoC не
закреплены исполняемым контрактом. Нужна небольшая структура, с которой можно
воспроизводимо проверить один сценарий отравления долговременной памяти
тестового стенда и сохранить причинно-следственную цепочку в текстовом отчёте.

## What Changes

- Определяется установленная команда
  red-alert attack --scenario memory-poisoning.
- Для автоматизации фиксируется одна ручка стенда:
  POST http://localhost:8600/v1/chat/completions.
- В контракте PoC фиксируются авторизация Bearer, явный session_id,
  auth_mode=vulnerable и stream=false.
- Сценарий выполняет последовательность payload в сессии A, finalize в той же
  сессии A и trigger в новой сессии B.
- Финализация вызывается специальным сообщением finalize через chat completions.
  Прямой вызов POST /v1/sessions/{session_id}/finalize в Red Alert не выполняется.
- Каждый шаг сохраняется в трассировке вместе с безопасным представлением запроса,
  HTTP-статусом и текстом ответа.
- Результат выводится только как текстовый отчёт в стиле pytest. JSON-отчёт и
  опция --report в этот PoC не входят.
- Автоматические тесты используют изолированный mock transport или mock HTTP-сервер.

## Capabilities

- poc-cli: запуск одного поддержанного сценария через установленную команду.
- chat-completions-client: минимальный клиент точного chat completions контракта
  стенда.
- memory-poisoning-scenario: фиксированный многошаговый сценарий с переносом
  рабочей памяти в долговременную.
- attack-verification: проверка поведенческого эффекта после финализации.
- text-run-report: текстовый отчёт с шагами и доказательствами.

## Impact

План затрагивает будущий Python-пакет вокруг main.py, CLI, модели трассировки,
клиент HTTP, сценарий, проверку, отчёт и тесты. Реализация работает только с
авторизованным локальным тестовым стендом.

Страница GET http://localhost:8501/memory учитывается как ручной интерфейс
наблюдения: она возвращает HTML и требует браузерную SSO-идентичность. Она не
становится машинным API Red Alert и не вызывается автоматическим клиентом.

Стенд также предоставляет прямую ручку финализации
POST /v1/sessions/{session_id}/finalize, но она сознательно исключена из
контракта PoC, поскольку автоматизация должна использовать только
POST /v1/chat/completions.

## Зафиксированный объём

- Целевой режим стенда — auth_mode=vulnerable.
- Тело каждого запроса содержит отдельный массив messages с одной пользовательской
  репликой.
- Сессия A используется для доставки payload и финализации; сессия B имеет другой
  session_id и используется для trigger.
- В текущем PoC сессии выполняются под одним API-ключом и одним user_id. Проверка
  распространения на отдельный user_id и отдельный API-ключ остаётся следующей
  атомарной возможностью.
- Перед прогоном окружение стенда должно быть подготовлено в известном состоянии.
  Операция очистки памяти не входит в текущий change.
- Успех подтверждается поведением trigger после успешной финализации, а не прямым
  чтением базы или HTML-страницы памяти.
