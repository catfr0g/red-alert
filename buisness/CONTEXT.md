# Контекст кейса: agentic red teaming

> Рабочие определения терминов вынесены в [глоссарий](./GLOSSARY.md).

## 1. Формальная формулировка проблемы

### По тексту кейса
**Кто**: Департамент кибербезопасности банка — пользователь решения, который валидирует и тестирует системы генеративного ИИ.
**Когда / контекст** -  банк внедряет интеллектуальных ассистентов и автономных агентов с постоянной памятью, доступом к данным клиентов и инструментам, способным изменять состояние системы.
**Что хочет сделать** - Автоматически проверить, может ли атакующий незаметно изменить состояние агента так, чтобы тот позднее выполнил действие, выгодное атакующему.
**Что мешает / в чём боль** - Агент — это не только чат: атака может пройти через запрос, документ, веб-страницу или результат инструмента, попасть в контекст/память, повлиять на планирование, выбор инструмента или его аргументы и проявиться только в следующей сессии. Текущая проверка финального ответа не показывает такую компрометацию надёжно.
**Ожидаемое решение** - Прототип agentic red teaming, который автоматически проходит полный цикл: моделирует угрозу, генерирует и выполняет многошаговую атаку, наблюдает трассировку, проверяет достижение цели, анализирует скомпрометированное состояние и формирует отчёт с ASR.
### Более общая 
**Кто**: Бизнес, который предоставляет продукт в виде ии агента
**Когда / контекст** -  у агента появляется доступ к персональным данным, банковским счетам, обязанность к **рискованным** советам пользователю (медицина, психологическая помощь, юридические услуги)
**Что хочет сделать** - Просто развернуть агента и быть уверенным, что он корректно исполнит задачу без побочных рисков
**Что мешает / в чём боль** - обычно у агентов очень много компонентов (инструменты, MCP, RAG, подагенты, сжимание контекста, история взаимодействий, сама llm), все сценарии сложно проверить самостоятельно руками.
**Ожидаемое решение** - инструмент, подстраивающийся под продукт и находящий не только общие кейсы уязвимостей, но и частные.

### Аналоги ожидаемого решения

#### Решения исключительно для чат-ботов (формат запрос - ответ)
- Это фреймворки для red teaming LLM. Они генерируют вредоносные промпты (запрос) и анализируют текстовый ответ модели (ответ). Они не внедряются внутрь рабочего процесса (workflow), не перехватывают вызовы инструментов и не управляют состоянием агента. Их задача — проверить саму модель (или тонкую обертку API) на устойчивость к атакам, которые приходят на вход.
- 
**1. Garak** (https://github.com/NVIDIA/garak?ysclid=mtk5p2ivdf856562935)
- Атаки: DAN, Prompt Injection, GCG, Data Leakage, Toxicity, Malware Generation, XSS.
- Поддержка: Hugging Face, OpenAI, Bedrock, Replicate, GGML, REST, NIM.
- Логирование: JSONL с детальными данными каждой попытки.

**2. Promptfoo** (https://github.com/promptfoo/promptfoo?ysclid=mtk5qn3s2e339789054)
- Атаки: Более 50 типов, включая комбинированные джейлбрейки, атаки на основе кодирования (base64), многоязычные подходы, многошаговые взаимодействия, а также проверку соответствия OWASP и NIST.
- Поддержка: Практически все популярные LLM-провайдеры (OpenAI, Anthropic, Google, Azure, Bedrock, Replicate, Hugging Face), а также кастомные клиенты через HTTP API и end-to-end тесты с Selenium/Puppeteer.

**3. Llamator** (https://github.com/LLAMATOR-Core/llamator?ysclid=mtk5r80yfg122589712)
- Атаки: Prompt Injection, Jailbreaks, System Prompt Leakage, Misinformation, Unbounded Consumption.
- Поддержка: LangChain, OpenAI API, кастомные клиенты (Selenium, Telethon), Vision.
- Отчеты: DOCX, Excel/CSV.
  
**4. PyRIT** (https://github.com/microsoft/PyRIT?ysclid=mtk5ynh12i642910101)
- Атаки: Широкий спектр, включая инъекции промптов, джейлбрейки, атаки на основе GCG, а также оценку соответствия целям безопасности (например, генерация вредоносного кода, утечка данных). Предоставляет инструменты для создания кастомных атакующих стратегий.
- Поддержка: В первую очередь экосистема Microsoft (Azure OpenAI, Azure AI Studio), а также OpenAI API, Hugging Face и другие через модульную архитектуру. Акцент на масштабируемость и автоматизацию.
- Отчеты: Структурированные логи и JSON-отчеты, которые можно интегрировать в CI/CD для автоматического анализа.

#### Agentic Red Teaming
**1. PentAGI** (https://github.com/vxcontrol/pentagi)
- Назначение: Полностью автономная система ИИ-агентов для автоматизированного пентеста и Red Teaming . Позволяет проводить многоэтапные атаки, эмулируя работу команды профессиональных пентестеров: автоматически сканирует уязвимости, разрабатывает эксплойты и строит сложные цепочки атак на целевые системы .
- Архитектура и подход: Построена на мультиагентной архитектуре с распределением ролей — оркестратор проектирует цепочку атак, исследователь собирает разведданные (через поисковики и базы уязвимостей), разработчик пишет кастомный код эксплойтов, исполнитель запускает 20+ профессиональных инструментов безопасности (Nmap, Metasploit, SQLmap) в изолированных Docker-контейнерах. Использует гибридную память, имеет встроенную четырехуровневую супервизию агентов, поддерживает 10+ LLM-провайдеров (OpenAI, Anthropic, Google, AWS, Ollama и др.) через плагинную архитектуру.
- Ключевые особенности: Полностью автономная работа в изолированных средах — все действия выполняются в Docker-контейнерах, что исключает влияние на хост-системы. Включает граф знаний на Neo4j для отслеживания взаимосвязей между целями, уязвимостями и техниками атак. Имеет веб-интерфейс на React и REST/GraphQL API для управления задачами. Имеет более 8200 звезд на GitHub.

**2. HiveTrace Red** (https://huggingface.co/hivetrace)
- Автоматизированная платформа для adversarial тестирования GenAI-систем. Входит в экосистему HiveTrace, которая также включает мониторинг в реальном времени и защитные механизмы (guardrails). Инструмент позиционируется как продукт, но команда также развивает open-source guardrail-модели и датасеты для оценки безопасности.
- Архитектура и подход: Представляет собой конфигурируемый пайплайн, состоящий из последовательных этапов. В каждом запуске определяются: модели-атакующие (attacker_model), целевая модель (response_model) и модель-оценщик (evaluation_model). Использует датасеты атак (datasets) с возможностью подгрузки из файлов (CSV, TXT, Parquet, Excel), где каждый датасет имеет собственный evaluator для проверки ответов. Атаки (attacks) применяются к каждому промпту через кросс-произведение (cross-product), позволяя тестировать комбинации различных техник атак.
- Ключевые особенности: Интегрируется в CI/CD, обеспечивая непрерывное тестирование безопасности AI-приложений. Работает с любыми LLM-моделями (как открытыми, так и закрытыми) через универсальный конфигурационный интерфейс. Поддерживает полностью автоматический режим работы — от генерации атак до формирования отчета. 

**2. PharosOne** (https://github.com/pharosone/pharosone/blob/main/docs/architecture.md)
- Назначение: Поведенческий сканер уязвимостей для AI-агентов. Тестирует агентов на уровне их поведения: может ли агент быть вынужден раскрыть системный промпт, вызвать опасный инструмент с подконтрольными атакующему аргументами, довериться инструкции, внедренной в документ, или "отмыть" статус записи.
- Архитектура и подход: Построен на основе фреймворка Inspect AI. Использует корпус атак (probes), которые мутирует и прогоняет множество раз для статистической оценки успеха. Оценка производится с помощью детерминированного оракула и LLM-судьи, после чего результаты мапятся на стандарт безопасности AIUC-1.
- Ключевые особенности: Работает в офлайн-режиме без API-ключей. Поддерживает три целевых уровня: mock (полностью офлайн), model (реальная LLM с песочницей) и bridge (подключение к внешнему агенту через HTTP или асинхронный вызов). Включает развитую систему вариаций атак (вариации фреймов, обфускации) для обхода защит.

**3. AI-Infra-Guard** (https://github.com/Tencent/AI-Infra-Guard?ysclid=mtk5wvdlty442740527)
- Назначение: Комплексная платформа для Red Teaming AI-экосистем от Tencent Zhuque Lab. Охватывает сканирование AI-инфраструктуры (более 2000 CVE для Ollama, vLLM, ComfyUI и др.), безопасность агентов (Agent Scan), MCP-серверов и навыков агентов (Skill Scan), а также оценку джейлбрейков.
- Поддержка: Развертывание через Docker, веб-интерфейс, полноценный API, а также отдельные CLI-утилиты для сканирования навыков (aig-skill-scan) и агентов (agent-scan). Интегрируется с экосистемой OpenClaw.
- Отчеты: Подробные отчеты о сканировании с указанием уязвимостей, их серьезности и ссылками на устранение.

**4. Rampart** (https://github.com/microsoft/RAMPART?ysclid=mtk5zkpfs7578123979)
- Назначение: Фреймворк для тестирования безопасности агентных AI-приложений от Microsoft. Предоставляет структурированный, удобный для разработчика способ написания и запуска тестов безопасности для агентов.
- Особенности: Нативно интегрируется с pytest, что позволяет использовать знакомый разработчикам инструментарий. Покрывает как adversarial атаки, так и benign-сбои, а также широкий спектр категорий вреда. Использует оценку через LLM-судью и поддерживает распределенное выполнение тестов.

### Общая проблема текущий подходов
Типичный проверяемый объект при таком подходе:

```text
Запрос → ответ
```
Для рассматриваемого кейса нужна проверка более длинной цепочки:
```text
Входные данные → контекст → память → планирование → выбор инструмента
→ аргументы инструмента → результат инструмента → изменение состояния
→ последующие действия
```
### Что это стоит бизнесу

Точная денежная оценка в описании кейса не приведена — её нужно получить у кейсодателя. Уже видны следующие категории стоимости и риска:
- вредоносная инструкция может сохраниться в долговременной памяти и сработать в другой сессии;
- компрометация может затронуть другого пользователя или привести к распространению атаки;
- неправильный выбор инструмента или его аргументов может вызвать мошенническое действие либо доступ к конфиденциальной информации;
- проверка только финального ответа создаёт ложное ощущение безопасности: факт компрометации состояния может остаться незамеченным;
- `[Уточнить]` трудозатраты специалистов на ручное построение сценариев, настройку тестовых окружений и разбор трассировок;
- `[Уточнить]` стоимость одного прогона: время, вычислительные ресурсы и токены модели.

**Что стоит измерить на старте:** время подготовки одного сценария, долю сценариев, которые сейчас проверяются вручную, время до воспроизведения находки и потенциальный ущерб от затронутых действий.

## 3. Обязательные требования кейса vs наши предположения

| Обязательные требования кейса | Наши предположения, которые нужно проверить |
|---|---|
| Разработать прототип инструмента или доработать существующий open source-инструмент. | `[Предположение]` Быстрее начать с расширения одного из существующих инструментов, добавив агентный harness и слой состояния. |
| Автоматизировать полный цикл: анализ приложения и моделирование угроз → генерация атаки → выполнение → наблюдение за трассировкой → проверка цели → анализ скомпрометированного состояния → отчёт. | `[Предположение]` Для MVP достаточно одного воспроизводимого вертикального среза, а не покрытия всех типов агентов. |
| Тестировать внутреннюю цепочку агента, а не только диалог «запрос → ответ». | `[Предположение]` Цепочку можно инструментировать через API, middleware, логи или mock-инструменты целевого агента. |
| Поддержать доставку атаки через пользовательский запрос, документ, веб-страницу или результат инструмента. | `[Уточнить]` В MVP обязательны все четыре канала или допустимо начать с одного-двух. |
| Находить атаки, которые изменяют состояние или долговременную память агента. | `[Предположение]` У тестового окружения есть безопасный способ читать, сравнивать, сбрасывать и восстанавливать память/состояние. |
| Проверять влияние атаки на последующие сессии и других пользователей. | `[Предположение]` Можно запускать несколько изолированных сессий и различать их пользователей, tenant'ы и права. |
| Проверять влияние на принятие решений, выбор инструмента и аргументы вызова. | `[Предположение]` Доступны схемы инструментов, разрешённые действия и фактические вызовы с аргументами. |
| Учитывать дальнейшее распространение компрометации. | `[Уточнить]` Какой уровень распространения считать достаточным доказательством: следующая сессия, другой пользователь, другой инструмент или цепочка из нескольких действий. |
| Использовать Attack Success Rate (ASR) как целевую метрику — долю успешных атак. | `[Уточнить]` Что именно является успехом: запись в память, срабатывание триггера, опасный вызов инструмента, изменение состояния, утечка данных или комбинация условий. |
| Ориентироваться на департамент кибербезопасности как пользователя решения. | `[Предположение]` Основной интерфейс — отчёт/CLI или dashboard для специалиста, а не продукт для конечного клиента банка. |

## 4. Что знаем о данных и доступах

| Уже известно из кейса | Нужно получить или подтвердить |
|---|---|
| У агентов есть постоянная память: контекст диалогов, цели, данные клиентов, списки разрешённых действий и другие сведения. | Какой именно агент или mock-система является целевым стендом для демо: модель, версия, API и окружение. |
| Возможные источники атаки: пользовательский запрос, документ, веб-страница и результат инструмента. | Доступ к API/SDK агента и формат его конфигурации: память, инструменты, политики и права. |
| Важные этапы для наблюдения: контекст, память, планирование, выбор инструмента, аргументы, результат инструмента и изменение состояния. | Есть ли трассировка каждого этапа, включая prompt'ы, tool calls, ответы инструментов, записи памяти и идентификаторы сессий/пользователей. |
| Угроза может проявиться позднее, в другой сессии или у другого пользователя. | Можно ли создавать синтетические данные, тестовые документы и веб-источники; запрещены ли реальные клиентские данные и production-действия. |
| В качестве результата требуется отчёт с демонстрацией многошаговой атаки и анализом состояния. | Как читать, изменять, снапшотить и безопасно сбрасывать долговременную память; можно ли поднимать отдельные копии окружения. |
| Пользователь решения — департамент кибербезопасности банка. | Каталог инструментов, их схемы аргументов, разрешения, mock/stub-версии и безопасные аналоги финансовых операций. |
| Целевая метрика — ASR. | Набор эталонных сценариев, baseline на текущих инструментах, число попыток на сценарий и правила подсчёта ASR. |
| MITRE ATLAS и современные модели угроз для агентных систем названы релевантным контекстом. | Ограничения по размещению, секретам, журналированию, стоимости прогонов и возможности использовать внешние/локальные модели. |

## 5. Гипотезы для проверки

Все гипотезы ниже пока не проверены. Метрики и пороги успеха нужно зафиксировать после ответов кейсодателя.

| ID / тип | Гипотеза | Как проверить | Сигнал успеха |
|---|---|---|---|
| H1 — продуктовая | Специалистам кибербезопасности нужен отчёт об атаке на уровне состояния и действий агента, а не только оценка ответа. | Дать специалистам один и тот же результат в response-only и agent-trace формате и попросить подтвердить риск и воспроизвести находку. | Специалист может понять, где произошла компрометация, и повторить её по отчёту. |
| H2 — AI | По схеме приложения, инструментов, памяти и модели угроз AI сможет генерировать правдоподобные многошаговые цепочки атак через разные каналы доставки. | Запустить генератор на синтетическом агенте с заранее известными уязвимыми путями и провести экспертную оценку сценариев. | Генерируются сценарии, которые действительно достигают заданной цели, а не только вызывают подозрительный ответ. |
| H3 — AI | Адаптивный планировщик, учитывающий промежуточную трассировку, найдёт больше успешных путей, чем фиксированный набор prompt'ов. | Сравнить adaptive и fixed execution на одном наборе сценариев и одинаковом бюджете попыток. | ASR и/или покрытие уникальных путей выше у адаптивного режима при приемлемом числе ложных срабатываний. |
| H4 — продуктовая | Сравнение состояния до и после атаки, а также replay следующей сессии, позволяют доказать poisoning памяти и его последующее влияние. | Сделать снапшот, доставить вредоносную инструкцию, завершить сессию, запустить триггерную сессию и сравнить состояние/действия. | Отчёт показывает запись, триггер и последствие с привязкой к конкретным шагам трассы. |
| H5 — AI/оценка | Цель атаки можно проверять формально по предикатам состояния и вызовов инструментов, дополняя их AI-оценкой, даже когда финальный ответ безвреден. | Задать цели вроде «изменён аргумент инструмента» или «инструкция записана в память» и сравнить rule-based и LLM-оценку. | Успех определяется по фактическому состоянию/действию, а не теряется из-за нормального финального текста. |
| H6 — продуктовая | Единый формат сценария, доказательств и ASR позволит сравнивать версии агента и результаты повторных прогонов. | Прогнать один набор атак на двух версиях/конфигурациях тестового агента. | Результаты воспроизводимы, различия видны, а отчёт можно использовать как regression test. |
| H7 — **самое рискованное предположение** | Целевой агент можно безопасно и достаточно полно наблюдать: читать/сбрасывать память, перехватывать tool calls, видеть изменения состояния и запускать изолированные сессии. Без этого ASR и доказательство скрытой атаки будут ненадёжны. | На первом техническом спринте подключить минимальный стенд и проверить полный цикл «seed → attack → new session → observe → reset». | Есть надёжный контрольный стенд, на котором можно воспроизводимо подтвердить или опровергнуть компрометацию без реальных финансовых операций и клиентских данных. |
